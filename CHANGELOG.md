# Changelog

What changes for someone who runs Davy, per release. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and versions follow [Semantic Versioning](https://semver.org/). How to add a line is in `CONTRIBUTING.md`.

## Unreleased

### Security

- Scrub credentials, sensitive keys, credit cards and standalone IP addresses by default. Scrubbing runs on the server before storing or indexing ingest. E-mail and personal identity filtering are opt-in. Keys with look-alike letters, such as a Cyrillic `о` in `password`, match as their Latin form. Configure each project with `davy project scrub`; the admin HTTP API can only tighten a policy, and every change is logged. MCP project status reports the policy. Existing records are unchanged.
- An SDK client report can no longer add to the counts Davy keeps of what it refused itself. Davy writes those under reasons that start with `davy_`, and a report with such a reason, which anyone with a project's DSN could send, was stored as if Davy had written it. Davy now skips those entries. Rows stored before cannot be told apart from Davy's own.

### Added

- Drop rules for logs. A person drops the log lines of a project that nobody needs before they are stored: `davy drop add --data DATA SLUG` with exactly one of `--pattern ID` (its lines below warn, or with `--any-level` all of them), `--level LEVEL` (that level and every lower one, never a line whose level was missing or not understood) and `--message TEXT` (a substring, or with `*` a glob over the whole message), optionally `--service NAME` and `--keep N%`, which keeps exactly N of every 100 lines, the first one included. Per project the first live rule that matches decides. `--shadow` drops nothing and counts, per day, the lines and raw bytes the rule would drop among the lines no live rule took. `davy drop list` shows the rules in order with what each dropped or would drop in the last 7 days, `davy drop live`, `davy drop shadow` and `davy drop remove` change them, and a change reaches the log writer within 5 s. `davy drop live` shows the rule and what it would have dropped in 7 days and asks before it goes live; `--yes` skips the question, and without a terminal it refuses unless given `--yes`. These commands never create or upgrade a store. A rule's text may not hold invisible characters, and a list quotes it. The MCP tool `usage` and `davy usage` show `logs_filtered` per project: the lines live rules dropped, by day of receipt, which still count in `logs`. An agent adds, lists and removes shadow rules over MCP with `drop_rule_shadow`, `drop_rules` and `drop_rule_remove`, at most 10 per project, each for 14 days, and each answer names the `davy drop live` command a person runs to make a rule live. An agent cannot stage a rule on Davy's own project, nor a level rule at warn or above. A person who adds a rule equal to an agent's shadow rule takes it over, so it no longer expires. Only `davy drop` writes a live rule or makes a rule live; no MCP tool or ingest path can. Adding a rule equal to one in the other state is refused with the command that turns it. The savings view of one project gives a pattern below warn that no rule names a share to keep, 1%, or 10% when a search asked for it, with `saves_per_day`, the `davy drop add` command a person runs and the `drop_rule_shadow` call that counts it first, or says which live rule decides its lines already. It lists each shadow rule with what it would have dropped in the window and the `davy drop live` command; a rate a day once the rule has counted a full day since its first counted day, its hours before; and no command for a rule that could hide warnings, errors or Davy's own lines, but what it would hide. Rules apply to Davy's own project too: a shadow rule hides none of its lines, and a live rule a person made drops the lines it names, warnings and errors included, while crashes are issues and never dropped. A project holds at most 50 rules, compiled once per change. Measured on an Apple M2 Max, `cargo run --release --example drop_judge` gives 1.9, 70.7 and 327.4 ns per line for 0, 10 and 50 rules that never match, and 0.15 ms for 50 rules on a 64 KiB message; `examples/fill_logs DATA 300000 24 4 RULES` gives a median of 9.65, 9.64 and 9.57 µs per record, within the noise of a run. The counts are kept 400 days. The upgrade adds the `drop_rules` and `drop_daily` tables as schema version 24.
- A savings view: where logs and errors could take less. The MCP tool `usage` with `view: "savings"` and `davy usage --view savings` list the log patterns with the most bytes and when a search last asked for each, the projects whose searches of the last 30 days read far less than they keep, with the retention that fits, the bytes the days it frees take, the `davy project retention` command a person runs to set it and a `count_logs` call over those days to try first, and the issues that send a fifth or more of a project's error events, at least 100, with the `davy issue discard` command and a word that discarding also stops storing the issue's real events. The retention fit reads the per-day search counts, which the 10,000-row trim of the search history leaves alone, and suggests nothing for a project with no recorded search in the 30 days, as reads by `davy logs` and `issue_context` are not recorded. Commands put their options first and the slug after `--`. `top`, 3 by default and at most 20, bounds each kind. `last_queried` is approximate: it matches the newest 1,000 searches' filters against a pattern's example, not the lines they returned, and the answer says so. Davy's own project has pattern entries but no retention or issue entry. The view changes nothing: a person runs the command shown. The summary stays the default view.
- Davy records the log searches people and agents run: `search_logs` and `count_logs` over MCP and the first page of a search on the web UI's logs page, with their filters, in the new `searches` table, and counts them per day with the oldest read in `search_days`. It keeps the newest 10,000 searches and 90 days of both, records a query over 1,000 bytes without its text, and a full writer queue drops a search rather than make a reader wait. The search text is kept up to 90 days and the MCP `sql` tool can read it. The savings view reads them.
- Discard an issue. `davy issue discard ID --data DATA` stops storing the issue's new events: each one is counted per project and UTC day, `davy usage` and the MCP tool `usage` show the count as `errors_discarded`, and the event is dropped. The events stored before stay until retention deletes them, and retention keeps the discarded issue so the mark holds. `--undo` stores the next event again, and forgets an issue left with no event and no feedback, as retention would. `errors_discarded` counts events received, so an SDK's resends count once each. `davy issues --json`, `davy context` and the MCP tool `issue_context` give `discarded_at`, the `davy issues` text view and the web UI mark a discarded issue, and `davy issues --discarded` lists them. Only a person can discard, at the CLI: no MCP tool can, and ingest never sets the mark. A crash issue of Davy's own project can be discarded too. JSON printed at the CLI writes C1 controls and bidi marks in titles as `\u` escapes. The upgrade adds a column to `issues` and the `discarded_daily`, `searches` and `search_days` tables as schema version 23.
- Davy monitors itself. `davy serve` records its own warnings and errors, such as a day of logs retention skipped or a failed commit, as logs of a project of its own in its own store, `davy`, or `davy-self` when a project of yours already has that slug, so an agent finds them with `search_logs` and `log_patterns`. Each line still goes to stderr. The project is made when `davy serve` starts, before its writers, with 30 days of logs and e-mail and personal data scrubbed, and counts in usage like any project. The disk forecast leaves its lines out, measured at 191 raw bytes on a quiet server's first day and none after, so a server that stores only errors keeps its forecast on errors alone and Davy's 30 days of logs do not lengthen the forecast's longest retention. Davy's own lines never wait: they are dropped and counted when their queue of 1,024 is full, and one kind of line is recorded 10 times an hour, with the rest counted. A panic becomes an issue of that project with a Rust backtrace and the release `davy@` and the version: the panic hook saves it in DATA/crashes first, at most 20 files of 64 KiB, so a panic that ends the process is recorded at the next start. A crash file is deleted only once the store has its event, and one that cannot be read is set aside in DATA/crashes/refused. A Linux release binary carries the line tables of Davy's own code, so Davy's frames name file and line, and grows by about 8 MB to 42 MB on aarch64; a macOS release binary carries none, so its frames name functions only, and stays at about 31 MB. No path of the build machine is in a release binary. `project_status` shows, whatever the slug, Davy's own warnings, errors and crashes recorded in the last 24 hours and the crash files that wait, or an `error` when they cannot be read, and `davy doctor` warns on a crash recorded in the last 24 hours with the `davy context` command and the `issue_context` call that show it. `project_status` and `davy doctor` name the project, and the MCP instructions and tool descriptions say where it is. The upgrade marks the project in `projects.own` as schema version 22. `davy serve --no-self-report` turns it off.
- Logs from Vercel Log Drains. A drain's custom endpoint `https://<davy>/vercel/logs` takes JSON or NDJSON with the project key in an `Authorization: Bearer` header. Each log keeps Vercel's fields as attributes under their own names, such as `attributes.source` and `attributes.proxy.statusCode`, takes `projectName` as its service and Vercel's trace and span ids, and counts in usage like any log. The endpoint follows Vercel's documented log schema and signing and has not yet been checked against a live drain. [Send logs from Vercel](docs/connect/vercel.md) shows how.
- A project can check Vercel's drain signature. `davy project vercel SLUG --secret-stdin` stores the drain's signature verification secret, read from standard input without the space around it and never printed. Then a request to `/vercel/logs` for the project needs an `x-vercel-signature` that matches the body exactly as sent, or it is refused with `403`. The check covers `/vercel/logs` only: the same project key still writes through `/`, `/v1/logs` and the envelope routes, so give each drain a Davy project of its own, whose key is only in the drain's header. Without a secret the project key alone lets a drain in, as for other log sources. `--no-secret` turns the check off. The upgrade adds a column to `projects` as schema version 21.
- A disk forecast for a server that stores only errors. When Davy counted no raw log bytes in the last 30 days and the disk holds no closed log day, logs add nothing, and the forecast rests on each project's errors with the new basis `errors_only`, where such a server had no forecast before. Its confidence is high once SQLite growth measured bytes per event on 7 days, medium while the footprint benchmark fills in, and low while errors that began less than a whole day or 7 whole days ago add over 5% of the errors' growth. Logs that came but have no log forecast yet, such as a first log line on an old server, count as 0 at low confidence where errors grow, and the summary says the disk may fill earlier once they count. A log retention what-if on such a server says that logs count as 0, and `davy doctor` drops the log default from its line. `full_on_range` runs at the errors' bound and estimate growth, and a what-if of `logs_bytes_per_day` adds logs on top of the errors. `davy usage` prints the errors' rate in its `range` line, and `davy doctor` warns and fails on the forecast as on any other, with `--errors N` in its fix. A server with neither logs nor recent errors still has no forecast, and the reason now says nothing grows yet. Servers with logs answer as before.
- Errors in the disk forecast, an estimate per project and "beyond 10 years". Each project's error events now grow SQLite until the project holds its error retention, at its events per day over the last 7 closed days and the bytes per event SQLite's daily growth measured, or the footprint benchmark until 7 days with 10,000 or more new events measured it. The MCP tool `usage` and `davy usage` gain `estimate`, which keeps each project's logs as long as that project keeps them, splits the growth by each project's raw bytes and takes all logs to pack alike, so a what-if for one project now shows what it does; it is never earlier than the bound, and `estimate.clamped` says when it took the bound's day. Events per day count from a project's first errors, so errors that began yesterday on an old project are not spread over 7 days. A what-if that lowers the longest log retention frees the closed days it deletes, in the bound too. `basis.errors` says what errors add, and confidence falls from high to medium when, before 7 days measured their bytes per event, they add over 5% of what the bound adds until the disk fills, or of the room left to the limit within 10 years where it never fills. A disk that fills more than 10 years out reads "beyond 10 years" with `disk.beyond_10_years`, not a date. `davy doctor` takes a disk full beyond 10 years as never full, still decides on the bound alone, and names the estimate's day where it differs. A worst case under 2 days only warns where the estimate puts the disk full later than the bound or not at all.
- A log forecast from the first hour. The growth of logs on disk is the raw bytes Davy counts per day times how they pack, measured on the server's own closed days and blended with the footprint benchmark until there are enough of them, as many as the shortest log retention lets the server keep, at most 7. A new server forecasts after an hour of logs, with a wide range and low confidence. Raw bytes per day are the larger of the median and the mean of the newest 7 whole days, so a server busy on 3 days of 7, or back from days without logs, is not read as quiet. A server that went quiet keeps its busy rate for 3 quiet closed days, falls from the 4th and grows at its quiet rate from the 7th. A server upgraded from a version that did not count raw bytes, told by closed days without a count, keeps the forecast from its disk sizes until its own days catch up. The MCP tool `usage` and `davy usage --json` gain `basis`: what the growth rests on, its low, middle and high, the confidence and `full_on_range`, the earliest and latest day the disk fills. `davy usage` prints it as a `basis` and a `range` line. The forecast decides on the high growth of a blend or a first day, and `why` says why confidence is low. `davy doctor` only warns on a first day forecast while the disk has days left, and asks to run it again once a whole day has closed.
- Count what Davy stores. The log writer counts the records and raw bytes of the logs it stores per index day and project once their day's commit holds, keeps the counts 400 days, past log retention, and as long as their logs are kept, and marks the days and projects retention deleted. The sweep writes SQLite's live size and the events kept once a day. The MCP tool `usage` and `davy usage` show `logs_stored` per project next to `logs`, which counts what clients sent by the day Davy accepted it. The upgrade adds the `log_days` and `store_days` tables as schema version 20.
- See what fills the logs: MCP `log_patterns` and `davy logs --patterns` list the line shapes with the most bytes in a window, each with an example, records, share, levels and services. `search_logs`, `count_logs` and `davy logs` filter by a pattern's id. Each day directory gains a `patterns-<project>.json` per project, at most 1,000 patterns per project and day, and past the first 500 only patterns seen 3 times that day. Logs indexed before this version have no pattern. A report names the days whose counters could not be read in `unread` and those whose counters started again from nothing in `restarted`.
- Usage and a disk forecast. Davy counts the records and bytes it accepts per day, project and signal (errors, logs, sessions, feedback, check-ins) and keeps the counts 400 days. Data counts once a queue took it, even when the client hangs up before the writer answers or the writer later turns an item down. The MCP tool `usage` and `davy usage` show what each project sent, how fast all logs together grow, the most retention lets Davy take and the day the disk fills, with a what-if for another log retention or total daily volume. Logs of all projects share one index per day, so the forecast caps the measured growth with the longest log retention of any project. When projects keep logs for different times, the day it names is marked as a worst case: at the current rate of logs, the disk fills on it or later, or never. The disk walk behind it never follows a symbolic link, stays on the filesystem of the data directory and reads at most 1,000,000 entries for at most 20 s, so logs kept behind a link or on another mount are not measured. What it cannot read, such as `lost+found`, or does not reach in its limits makes the measurement partial, not an error: the answer names what was left out, and gives no forecast when that is part of the logs. The server walks at most once a minute and shares that walk among the callers of the MCP tool, who wait for it without holding a thread, and for at most 30 s. `davy doctor` warns when the disk is forecast full in under 14 days and fails under 2, or for a worst case only warns until the disk is past its limit, and takes a disk past its limit while Davy no longer grows as never filled by logs, with a note to watch free space, warns with a fix for the reason when the forecast is missing for anything but too little history, and takes `--log-retention-days` like `davy usage` for a server not on the default 30 days; both say which default they assumed when a project has no retention of its own. Counts are written every 5 s in a transaction of their own and kept in memory until written, so a crash loses the last 5 s, or more while the writer is behind. The upgrade adds the `usage_daily` table as schema version 18, so like any upgrade it waits for the old server to stop.

- Follow Android, Rust and ASP.NET Core connect guides with DSN storage and SDK-specific limits.

- Agents can retrieve connection instructions and confirm ingest with MCP `connect_project` and `project_status`.

- Connect an app with `davy connect` JSON SDK instructions and a test-event command; list projects with `davy project list`.

### Added

- Retention per project, and a retention for errors. `davy project retention SLUG --logs 7 --errors 365` sets how many days a project keeps its logs and its errors, and `default` returns it to the server's. Agents can only lengthen it, with the new MCP tool `set_retention`, and cannot return a project with its own retention to the server default, because a shorter retention deletes data for good and an agent's prompt can carry text from someone else's error. The UI API changes it with `POST /ui/api/retention`, and `project_status` shows the days in effect. A change from the CLI waits for a log deletion under way, through a lock on the data directory itself, which the server can always open whoever ran the CLI. The CLI waits at most 5 minutes for it and the log writer 2 s, so a stopped CLI cannot stop logs being written. Settings the log writer cannot read stop its deletion, and it tries again within seconds. `davy serve --error-retention-days` sets the server default for errors, 36,500 days, so nothing stored is deleted until someone sets a shorter retention. Errors expire by when Davy received them: their issue's event count, hourly counts, first and last seen times and environment and release filters follow, and an issue whose last event expired is deleted once its user feedback is unlinked, 50 rows at a time, or has expired. If the error comes back it is a new issue with a new ID and a new-issue alert, or, while its feedback is still being unlinked, the old issue started again as unresolved with a new-issue alert, and an issue ID is never given out twice. The upgrade adds two columns to `projects`, two indexes on `events`, one on `issues`, a column and an index on `issue_tags` filled from the events, and the `id_floor` table. Filling the column took 0.4 s over 300,000 events on an M2 Max. The upgrade runs in one transaction before the server answers, so a database with tens of millions of events waits about a minute, and needs free disk for the new index. Under systemd the server reports it is ready only once the upgrade is done, and systemd stops a start that takes longer than 90 s and starts it again from the beginning, so before upgrading a large database run `sudo systemctl edit davy` and add `TimeoutStartSec=15min` under `[Service]`. Going back to an older Davy after the upgrade means restoring the backup taken before it.
- Davy refuses a data directory that a newer Davy has upgraded, and says to run that release or a newer one, or to restore the backup taken before the upgrade. An older Davy on newer data ignored what it did not know, so it could delete logs a project keeps longer than the server default and give a new issue the ID of a deleted one.
- Release health. Davy counts the sessions the Sentry SDKs send, per release, environment and hour, and the `release_health` MCP tool returns crash-free sessions and users per release, newest first. Browser and mobile SDKs send a session per visit, server SDKs count requests. Each session counts once however many updates its SDK sends, users are stored as a hash of the SDK's user id, and the counts are kept 90 days. Davy counts at most 1,000,000 sessions per project and day, because the DSN of a browser app is public.
- `count_logs`, an MCP tool that counts the logs matching the filters of `search_logs` per time bucket, so an agent sees how often something happens and since when without reading the logs. The CLI has the same as `davy logs --count`.
- User feedback from the Sentry SDKs' feedback widget, `Sentry.captureFeedback` and the older `user_report` item. `issue_context` shows the newest 10 messages about an issue, and the `user_feedback` table holds all of them. Davy keeps up to 1,000 per project and day, because the DSN of a browser app is public.
- Client reports from the Sentry SDKs: how many errors, logs and transactions an SDK dropped before sending, and why, such as `before_send` or a full queue. They are added up per project and day in the `client_reports` table and kept 90 days, so an agent can tell an app without errors from one whose SDK throws them away.
- Cron check-ins from the Sentry SDKs. A job wrapped in `Sentry.withMonitor` or reporting with `Sentry.captureCheckIn` becomes a heartbeat monitor with the schedule it sends, a crontab in its time zone or an interval, and gets the same incidents and alerts: a missed run, a run past its maximum runtime and a failed run each open one. Check-ins create up to 100 monitors per project and never change a monitor made with `davy monitor add`, which takes them with the new `--slug`. The DSN is public, so anyone who has it can change the schedule of a monitor made by check-ins, and `davy monitor list` counts those changes. Notices of these monitors reach a channel as one `monitor.digest` at most every 30 s and never hold back other alerts. A channel that drops them because 100 wait counts them in a column of their own, `sdk_dropped` in `davy channel list` and its `--json`, the Alerts page and the `sql` tool, so a flood from someone with the DSN never moves `dropped`, which counts only lost issue, feedback and operator notices. Resolved incidents and sent notices are kept 30 days. [Connect a Node app](docs/connect/node.md#cron-jobs) shows how.
- `davy monitor edit` changes a monitor in place: its name, schedule, URL, keyword, timeout, grace period, slug or project. Only the given flags change, and the monitor keeps its ID, checks, incidents and heartbeat token, so a cron job that pings it needs no change. A monitor moved to another project brings its open incident, and that project's channels hear of it. A monitor keeps its kind, and one made by check-ins only takes a new name, because its check-ins set the rest.

### Changed

- A log line's level is read in more spellings: `severe`, `fault`, `failure` and `exception` as error, the single letters `T`, `D`, `I`, `W`, `E` and `F`, a pino number sent as a string such as `"50"`, and a name in brackets, with a colon or after a dot, such as `[error]`, `error:` and `Level.ERROR`. Such lines were stored as info before; lines already stored keep their level.
- An event's release longer than 200 characters, environment longer than 64, or user ID longer than 256, is dropped and the event kept without it. Each was stored whole in a column, and a release and an environment also in a tag and the releases list, from a DSN that may be public, and a user ID of a megabyte made one retention batch free far more pages than it counted.
- **Breaking:** issue notices to one channel now wait up to 30 s, and several go out as one digest such as `[shop] 12 new issues` with the first 5 titles and their links. A test run that made 13 issues sent 15 messages in a second. A webhook receiver that acts on `issue.new` or `issue.regressed` must also handle `issue.digest`, whose `issues` array holds each issue with its type, project and link. A single issue notice and monitor notices go out as before. The upgrade adds a column to the `notifications` table.
- Log search keeps the day indexes it opened open between searches. Over 90 days of logs, a search for one request ID took 88 ms and now takes 2.3 ms. The first search after a start still opens each day once.
- Each 10 s sweep deletes expired checks, incidents, notifications and check-in starts 1,000 at a time until none are left or it has spent 100 ms, instead of at most 1,000 of each. On an M2 Max a sweep deleted about 60,000 rows where it deleted 3,000, so check-ins flooded in from many projects' public DSNs no longer pile up faster than they expire.

### Fixed

- A write of the server no longer fails with `database is locked` when the CLI, such as `davy resolve` or `davy project retention`, writes at the same moment. A batch that read before it wrote could not wait for the CLI's write, so every job in it failed, events included. It now waits up to 5 s for it.
- A symlink or a file in the place of a day of logs, or a directory with another name for a date such as `+002026-01-05`, is no longer searched or written through. Log retention never deleted from one, but kept it without a word; it now reports each on stderr, with its path quoted and escaped, again if it comes back after it was moved away, and `davy doctor` warns about it. A log of such a day is dropped with an error and the batch's logs of other days are written, where before one failed the whole batch. A directory named for a year of six digits was taken for a day and could be deleted whole.
- A new version no longer migrates the database while the old server still has it open. Any `davy` command of a new version that opened the store ran the migrations, and the old server kept writing under the old schema. Now a command whose version must migrate waits up to 10 s for other processes to close the database, then stops with an error and changes nothing. Stop or restart the old server on the new version. Two commands of the same version that start together, such as `davy serve &` and `davy project create` on a fresh directory, no longer fail with `database is locked`: they take turns through a lock on the new file `davy.sqlite.lock` beside the database, so eight that start at the same moment all get the migrated store. When no migration is pending, the server and the CLI share the database as before.
- Commands that only read no longer create or upgrade the database. `davy sql` and `davy project list` created `davy.sqlite` in a data directory without one, and they and `davy doctor` ran pending migrations on a database an older Davy wrote, from a path meant to only read. They now open it read-only, and a missing database, one from an older or newer Davy, or a stopped server's directory on a read-only mount, where SQLite cannot create the file it reads through, is an error that says what to do.
- A burst of new issues can no longer drop a monitor alert. Issue notices and monitor notices shared one channel's 100 unsent places, so anyone with a public DSN who sent 100 new errors within the 30 s digest window made Davy drop the next `monitor.down`. Issue notices now have 100 places of their own.
- A bare word in a log search now finds attribute values at any depth. Searching `r-3fa9c2d1` found nothing when the request ID sat in `attributes.req.id`, and only `attributes.req.id:r-3fa9c2d1` found it. Logs written before this release keep the old behaviour: a bare word matches their message only.
- An issue's latest event is now its newest one. After 50 events Davy kept the payload of only every 100th, so the UI, `davy event` and `issue_context` could show an event hours older than the issue's last seen time. The newest event's payload sits in the new `latest_payloads` table until a newer event replaces it, so a busy issue takes the disk of the 150 payloads in 10,000 it keeps: 271 bytes per event over 10 issues of 10,000 events on an M2 Max. Reading an issue's latest event takes about 3 µs more. A `sql` query finds that payload in `latest_payloads.payload`, not `events.payload`. A data directory from a build of `main` that kept it in `events` took 2,169 bytes per event for the same issues: the upgrade moves those payloads, 3.3 to 4.0 s for 100,000 issues, and the space lost comes back as old events expire, or with `VACUUM` while the server is stopped. The upgrade moves them the first time a command of the new version that migrates opens the data, such as `davy serve` or `davy issues`, and like every migration it waits for the old server to stop. `davy sql`, `davy usage` and `davy doctor` open it read-only and leave the upgrade to such a command. It needs free disk of about twice the moved payloads.
- Davy removes terminal colour codes and other complete ANSI CSI and OSC sequences from log messages and string attributes as it takes them in, from every log route. Lines that `tracing_subscriber`, zigbee2mqtt and other tools colour now read as plain text, and a search finds the word after a colour code. Logs stored before this release keep their codes.
- The uptime chart no longer draws an hour with one failed check like an outage. A bar is now as tall as the hour's mean response, with the share of checks that failed in red at its top, and the hover reads `1 of 60 checks failed`. Only an hour an incident was open in is a full hatched bar. The hourly cells in `/ui/api/monitors` have a new `down` field for that.
- An HTTP check no longer fails with `connection closed before message completed` when the target closes an idle keep-alive connection just as the next check starts. Each check and alert delivery now opens a new connection, so a check's response time includes connecting and the TLS handshake, as for a new visitor, and is higher than before for targets that kept the connection open.

## 0.1.0 (2026-11-23)

The first release. One binary takes errors from the Sentry SDKs and logs from Logtail shippers and OpenTelemetry, checks uptime, sends alerts, serves a web UI for one team and gives coding agents MCP tools. Install it with [docs/install.md](docs/install.md) or the Docker quick start in the [README](README.md).

### Added

- **Errors.** Ingest from the Sentry SDKs through the envelope and `/store/` routes. Events group into issues, and a fixed issue reopens only when the error comes back in the fix release or a newer one.
- **Source maps.** `sentry-cli` uploads maps as it would to Sentry, and minified frames turn back into source by debug ID.
- **Logs.** Ingest from Logtail shippers (JSON and msgpack), OTLP/HTTP and Sentry's `log` item. Full-text search per UTC day, kept 30 days by default (`--log-retention-days`).
- **Uptime.** HTTP monitors with status and keyword checks, and heartbeats for cron jobs with a failure ping.
- **Alerts.** New issues, regressions and monitor incidents go to signed webhooks, Slack and e-mail over SMTP, with retries. Never one notice per event.
- **Agents.** An MCP server at `/mcp` with `schema`, `sql`, `search_logs`, `issue_context`, `mark_fixed` and `submit_feedback`, behind the admin token. `davy mcp-config` prints the config for Claude Code, Codex and Cursor. `davy feedback` lists what agents reported.
- **Web UI** at `/ui/`, for the people `davy user add` invites:
  - Issues: triage from the keyboard, a 24-hour strip per issue, resolve, ignore and reopen one issue or many.
  - An issue's events with stack traces, breadcrumbs, context and the logs around them.
  - Logs: search, filter by range, project and level, zoom on the histogram, live tail.
  - Uptime, Alerts with every delivery and its last error, Projects with each DSN and the code per SDK, Setup with the install steps Davy has seen, Account.
  - Light and dark, following the system.
- **Install.** `davy setup` prepares the data directory, the admin token and a launchd job or systemd unit in one command and can run again safely. `davy doctor` checks a running install and prints the fix for each problem, also as `--json`. `docs/install.md` is written for a coding agent to follow, with one page per SDK in `docs/connect/` and an index in `llms.txt`.
- **CLI.** `project`, `user`, `issues`, `event`, `context`, `resolve`, `logs`, `sql`, `monitor`, `channel` and `feedback`, each with `--json` where it prints data.
- **Downloads.** Static Linux binaries for x86_64 and aarch64, macOS binaries for Apple silicon and Intel, and the multi-arch image `ghcr.io/dominikzabcik/davy` on distroless as a non-root user. Each binary has a CycloneDX SBOM and build provenance, and the image is signed. [RELEASING.md](RELEASING.md) shows how to verify them.

### Performance

Measured on the release build:

- The issue list answers in under 30 ms at the 95th percentile with 100,000 issues.
- A page of logs answers in under 35 ms and a histogram of a whole day in under 50 ms at the 95th percentile with 10 million logs.
- When the ingest queue is full Davy answers 429 and the SDKs back off, and UI writes leave half of each write batch to ingest.

### Security

- An internal penetration test of the server found 1 high, 2 medium, 7 low and 6 informational findings. Two security reads of the fixes by other models followed. Every high is fixed. [The report](docs/security/pentest-0.1.0.md) lists each finding and what became of it.
- An internal penetration test of the web UI found 1 medium, 3 low and 7 informational findings, with two reads of the fixes after it. [The report](docs/security/pentest-ui-0.1.0.md) lists each finding and what became of it.
- Davy creates its files readable by its own user only, keeps the admin token and SMTP URL in files (`DAVY_TOKEN_FILE`, `DAVY_SMTP_URL_FILE`) and refuses a plain `http` MCP URL unless the host is a loopback address.
